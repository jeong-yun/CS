# /var 지속 증가 — 컨테이너 쓰기 레이어

- 발생일: 2026-08
- 대상: `<HOST>` / k3s 노드
- 상태: 원인 규명 완료 / 근본 조치 벤더 문의

## 증상

- `/var` 사용량이 일평균 약 +800MB 지속 증가
- 다른 노드에서는 같은 기간 수십 GB가 **감소** (동일 시스템, 서버별 상이)
- 디스크 사용률이 85%대에 접근

## 원인

**실행 중 컨테이너 4개의 쓰기 레이어(overlayfs upperdir)** 가 증가 주체.
컨테이너 내부의 볼륨이 아닌 경로(세션 로그·임시 데이터)에 기록되는 데이터가
호스트 `/var` 아래 containerd 스냅샷 디렉터리에 누적되는 구조.

증가분 귀속 (일 단위):

| 항목 | 일 증가 | 비중 |
|---|---|---|
| containerd 쓰기 레이어 | +455MB | 78% |
| kubelet 볼륨(단일 파드) | +100MB | 17% |
| 파드 stdout 로그(분산) | +29MB | 5% |

다른 노드의 **감소**는 kubelet 이미지 GC 발동으로 추정 (사용률 85% 초과 → 미사용 이미지
삭제 → 80%까지 회수). 즉 두 노드의 상반된 현상은 "임계 도달 여부"의 차이이며,
증가 자체는 양쪽 모두 진행 중.

## 조치 (확인 절차)

측정 → 분해 → 귀속 → 격리 순으로 진행. 각 단계가 가설을 하나씩 기각.

1. **증가 계량** — 일일 du 스냅샷 diff로 `/var` 하위 증가 디렉터리 특정
   (`sudo du -xm --max-depth=N` + awk 2-pass 비교)
2. **계층 분해** — `<K3S_ROOT>` → `agent/containerd` 하강.
   → `storage/`(PVC) 사실상 0 → **PVC 가설 기각**
3. **이미지 누적 여부** — `crictl images --digests`:
   dangling 없음, 태그 중복 미미 → **이미지 누적 가설 기각**
   → 남는 증가 요소는 쓰기 레이어뿐
4. **컨테이너별 크기** — `crictl stats -a`의 DISK 컬럼에서 GB급 4개 확인
5. **신원 대조** — `du`의 스냅샷 번호와 `crictl`의 컨테이너 이름을 **크기로 1:1 매칭**
   (단위 환산: MiB × 1.048576 = GB). 4쌍 모두 소수점까지 일치
6. **성장 주체 격리** — 시간 간격을 둔 2회 측정에서 **해당 4개만 증가, 여타 300여 개는 불변**
   → 보유량이 아닌 **증가 주체**로 확정
7. **재시작 배제** — `crictl ps`의 CREATED로 측정 기간 중 재시작 없음 확인

측정 중 발생한 오류와 교정:

- 비-sudo로 측정한 값(77GB)과 sudo 측정값(396GB)을 비교해 가짜 델타가 발생 →
  **비교는 동일 조건끼리**로 교정
- `find --size +100M` 기반으로 "증가 없음" 판단이 나왔으나, 다수 소형 파일로 자라는
  워크로드에는 적용 불가한 측정이었음 → 총량 시계열로 재판정
- `-h` 단위의 반올림으로 합산 검증이 어긋남 → 기록용 스냅샷은 `-m` 사용

## 재발 방지

- 일일 du 스냅샷 cron 등록, 깊이를 상향해 컨테이너 저장소 계층까지 자동 분리
- 쓰기 레이어 상위 N개를 **이름 기준**으로 일일 기록 (`crictl stats -o json`)
  — 컨테이너 재시작으로 스냅샷 ID가 바뀌어도 추적 유지
- 측정에는 시각을 함께 기록 (`date` + `tee -a`)
- 근본 조치는 **로그·임시데이터 경로의 볼륨 분리 + 로테이션 설정**.
  벤더 배포 차트 영역이므로 측정 수치를 근거로 공급사 요청
- 파드 재시작은 일시 회수일 뿐이며, 설정 미변경 시 동일 속도로 재증가

## 참고

- 실행 중 컨테이너의 쓰기 레이어는 **kubelet GC의 정리 대상이 아님**.
  방치 시 종착점은 자동 정리가 아니라 eviction(파드 축출 = 서비스 장애)
